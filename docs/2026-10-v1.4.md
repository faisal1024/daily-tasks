# 1.4

## Task-aware notifications

Reminders used to say the same fixed lines every day ("Today's Three still
need a little attention."). From 1.4 they say what the tasks are. Owner's
decisions: free for everyone; written on the phone (no AI, nothing sent
anywhere); task names shown by default, with a switch to hide them; the same
number of reminders at the same times as before.

Tone is unchanged: calm, no guilt, no red. Something unfinished is "still
open", never "missed" or "overdue".

### What they say

`lib/daily-tasks/reminder-copy.ts` is a pure builder:
`buildReminderCopy({ kind, dayKey, slotIndex, tasks, locked, yesterdayOpen, hideNames, certain, evening })`
returns `{ title, body, taskId? }`, or `null` when there is nothing to remind
about. It sends nothing anywhere.

The title changes with the situation. Often the title is the task and the
body is the situation; other variants keep the slot's own title ("A calm
start", "A small nudge", "Still time today") and put the task first in the
body.

| Situation | Title | Body |
| --- | --- | --- |
| None done | Call the dentist | First up today. Five minutes is a start. |
| None done, one task only | A small nudge | Today's one thing: Call the dentist. Five minutes is a start. |
| Some done, more than one open | Next: Write the report | 1 of 3 done. |
| Some done, one open | One to go: Walk | A small finish is still a finish. |
| The next reminder, in the evening | Still time today | Still open tonight: Walk. Five minutes still counts. |
| Written ahead (see below) | Write the report | Still open? A small start counts. |
| Written ahead, whole list | A small nudge | Today's three: Call the dentist · Write the report · Walk. Anything still open? |
| Written ahead, evening | Still time today | Walk. Still open tonight? Five minutes still counts. |
| Nothing set, one open from yesterday | Still open from yesterday | Renew passport. Want it in today's three? |
| Nothing set, several open from yesterday | A calm start | 2 still open from yesterday: Renew passport and Buy stamps. Want them in today's three? |
| Tomorrow morning, written today | A calm start | From yesterday: Walk. Still open? It could be one of today's three. |
| Nothing set, nothing left over | A calm start | Nothing picked yet. What are today's three? |
| Everything done | no reminder (as before) | |
| "Hide task names" on | the general titles | the general lines from before 1.4 |

- **The named task rotates.** The next reminder names the next task (the
  first still open, in Today's order). Each later one today names
  `open[slotIndex % open.length]`, so a day with three open tasks walks
  through all three. "From yesterday" lines take yesterday's open tasks in
  turn too, and some variants say the whole list.
- **Variants go by the slot's place in the whole day** (`reminderVariantIndex`:
  10:00 is the first, 17:00 the fifth; kinds are not counted apart), each
  one step on from the one before, so two reminders in a row never share a
  body, and a reschedule doesn't reshuffle them. The pools that have a
  whole-list line keep it at the same index, so two in a row never both read
  out the list.
- **A one-task day is never "first up"**: "Today's one thing: …" or "Just
  one today: …".
- **Evening slots (17:00 on) have evening wording**, also the progress
  reminders that "Every hour" sends into the evening.
- "Today's three" is only said of three tasks; otherwise "On today's list".
  Names that share a line are cut shorter (28 characters).
- Task text is made safe first (`reminderTaskName`): newlines, tabs, control
  characters and text-direction overrides become spaces, runs of spaces
  collapse, and anything longer than 60 visible characters is cut with an
  ellipsis. Cutting counts whole characters (an emoji, a flag, an accented
  letter), using `Intl.Segmenter` where it exists and a built-in fallback on
  Hermes. A name that already ends in ".", "!", "?" or "…" gets no second
  full stop. The scheduler cleans every plan's title and body the same way
  (`cleanReminderText` in `fitPlanToLimit`: 90 and 240 characters), so
  another strategy's words are safe too.
- "Still open from yesterday" comes from the tasks waiting on Today's
  "from yesterday" card (`yesterdayOpenTexts`). Ones already carried into
  today or let go are not mentioned, and neither is anything older than
  yesterday.
- The morning nudge on a day with a draft from the evening close still reads
  "Your three for Tuesday: A · B · C" (general wording when names are
  hidden). The draft's names are cleaned and capped like any other.
- A set (locked) day with nothing on it gets the general line: nothing can
  be added, so nothing is offered.

### When they are rewritten

iOS cannot run the app's code when a local notification is delivered, so
what a reminder says is fixed when it is scheduled. The store therefore
rewrites the pending reminders:

- when the app opens, and every time it comes to the front;
- when a task is added, ticked, unticked, removed, reordered or reworded;
- when the day is set or reopened, when the "from yesterday" card changes,
  and when the day changes;
- when a reminder setting or the notification permission changes.

Changes settle for 500 ms first (`REMINDER_SYNC_DEBOUNCE_MS`), so ticking
two tasks in a row or dragging costs one rewrite. If the app leaves the
front while a rewrite is waiting, it runs at once (a timer may never fire in
the background). A rewrite that fails is forgotten rather than taken as
done, so the next trigger asks for it again.

**How a rewrite is applied** (`runPlan` in `notifications.ts`): the plan is
scheduled first, then the owned reminders that are no longer in it are
cancelled. Ids are fixed by day, kind and time, and scheduling an id that is
already pending replaces it, so there is never a moment with nothing
pending; an interrupted rewrite leaves the old reminders, not none. A
pending reminder that already has the same title, body and time is left
alone. One failed schedule or cancel does not stop the rest (a failed
replacement removes the out-of-date one it was meant to replace). Only when
old and new together would pass iOS's limit are the old ones cancelled
first.

**Reminders that already went off** go stale in Notification Center (a
count that has moved on, a task since done). A rewrite clears the owned ones
that are showing whenever the app is in front, and when "Hide task names"
has just been turned on. Other notifications are never dismissed.

Each rewrite also schedules one morning nudge for each of the next six days
(as before). Tomorrow's is written from what is still open today, so it is
right even if the app isn't opened first: "From yesterday: Call the
dentist. Still open? It could be one of today's three.". "Yesterday" is
relative to the day it arrives. The days after that have nothing to go on
and ask plainly.

Times are unchanged: an empty day gets hourly morning nudges (8:00 to 12:00
on weekdays, 10:00 to 12:00 at weekends); a day with tasks gets 10:00,
12:00, 14:00, 16:00 and hourly 17:00 to 22:00 (or hourly 8:00 to 21:00 with
"Every hour"). All in the phone's local time; the next days' nudges use
calendar arithmetic, so a clock change keeps the local hour.

**When the store's day and the clock's day differ** (`reminderCopyContext`):

- Just after midnight the store can still be on the day before. Its tasks
  are then yesterday's: the new day is planned as an empty one, with the
  open ones "from yesterday". A store two or more days behind says nothing
  about its tasks.
- After flying west the store's day can be the clock's tomorrow. The rest
  of the clock's day still names its tasks, that day's own morning nudge is
  written from them (in the written-ahead wording; none if they are all
  done), and the morning after it gets them as "from yesterday".

Later: reminders are scheduled for an absolute moment (a date trigger), so
after a time-zone change the already pending ones arrive at the old zone's
hour until the app is next opened. Time-zone-following calendar triggers
would fix that; left for a later release.

### The widget-tick limitation

A task can be ticked from the widget without the app running, and the app
only learns of it when it next opens. A reminder scheduled before that tick
cannot know about it. So only the **next** reminder states the count or
says outright that something is open ("1 of 3 done", "One to go"); every
later one today, and tomorrow morning's, is task-first, present tense and
true either way: no counts, and "Walk. Still open? Five minutes is a
start.". Opening the app rewrites them all from the real state.

**The last tick.** When a tick made outside the app leaves nothing open
(the widget's `ToggleTaskIntent`, the Live Activity's Done in
`FocusActions.done`), the native code removes the app's pending reminders
for the rest of today (ids starting `daily-tasks:<today>:`) and tomorrow's
morning nudge (`FocusGroup.clearRemindersIfAllDone` in
`FocusActivityShared.swift`). The app schedules them afresh when it next
opens. Unticking on the widget afterwards does not bring them back until
then. This needs a check on a device: the widget's intent runs in the
widget extension, and it must be confirmed there that it reaches the app's
pending notifications.

What this still cannot fix: the next reminder (the plain one) may name a
task that was ticked on the widget since, if other tasks are still open.

### The 64 limit

iOS keeps at most 64 pending local notifications per app and silently drops
the rest. The reminders use 20 at most (14 with "Every hour" plus six
mornings; 16 by default). The scheduler still enforces it for any plan
(`fitPlanToLimit`): it counts the pending notifications that are not its
own (the focus timer's end, the trial reminder), always leaves room for at
least two of those, and schedules only the soonest reminders that fit. In
development it warns (with a count, never the words) when a plan has an id
outside the prefix, which is dropped.

The scheduler only ever schedules, cancels or dismisses notifications whose
id starts with `daily-tasks:` (`MANAGED_REMINDER_PREFIX`). The focus timer
(`three-today:focus-timer`), the trial reminder (`plus-trial-ending`) and
their categories are never touched. Tapping a reminder opens Today, as
before. A reminder that names one task carries `data: { taskId, kind }`
(the id, never the text).

### The privacy switch

Settings › Reminders › What reminders say › **Hide task names in
notifications** (off by default): "Reminders won't show what your tasks
are. Good if others can see your lock screen." With it on:

- every reminder uses the general titles and lines from before 1.4,
  including the morning nudge after an evening close; no title or body has
  task text;
- the focus timer's end notification is titled "Time's up" instead of the
  task ("5 more minutes, or mark it done?"), and flipping the switch
  reschedules a running session's;
- reminders already showing (which may name tasks) are cleared when it is
  turned on.

Not covered: the Live Activity and the widget show the task by design.
After "Keep going" on a starter's Live Activity the native side rewrites
the body as a timer's ("Time's up. 5 more minutes, or mark it done?") and
keeps the title, so a hidden one then says "Time's up" twice; no task text.

Stored as `notifications.hideTaskNames`; only a saved `true` turns it on, so
older saves and damaged values load as off.

Each reminder switch in Settings is one element to VoiceOver: the switch,
with the row's title as its label, the help text as its hint and its on/off
state. The visible text is hidden from VoiceOver so nothing is read twice.

The standard reminders are local notifications: written and scheduled on
the phone, with no task text sent anywhere to make them. No log line or
analytics event carries reminder text (ids and counts only).

### Plans and strategies

`lib/daily-tasks/reminder-plan.ts` separates what to schedule from
scheduling it:

```ts
interface ReminderPlanItem {
  id: string; // starts with "daily-tasks:"
  fireAt: Date;
  title: string;
  body: string;
  data?: Record<string, unknown>; // ids only, never task text
  kind?: string;
  interruptionLevel?: "passive" | "active" | "timeSensitive" | "critical";
  sound?: boolean | string;
}
type ReminderPlan = ReminderPlanItem[];
type ReminderStrategy = (context: ReminderContext) => ReminderPlan | Promise<ReminderPlan>;
```

- `taskAwareStrategy` is the standard one (the reminders above). It sends
  nothing. `ReminderContext` itself makes no such promise: a strategy that
  sends something must say so itself.
- `morningsStrategy` is the upcoming mornings alone, and
  `combineStrategies(morningsStrategy, another)` joins plans so the mornings
  and another strategy's slots coexist (the earlier strategy wins an id; if
  one fails the whole rewrite fails and is retried).
- A strategy may be async. The context carries `pending` (the owned
  reminders pending now, soonest first, with their time and words) and
  `lastDeliveredAt` (when one last went off, as far as is known). A
  strategy with times of its own choosing (random ones, at most one an
  hour) returns the pending ones it wants to keep with the same id, time
  and words, and the scheduler leaves them as they are instead of picking
  again on every sync.
- `syncNotifications({ ...context, strategy })` plans with a strategy and
  applies the result; `applyReminderPlan(plan)` applies any plan directly.
  One sync at a time. Every item's words are cleaned and the plan is cut to
  the 64 limit, whichever strategy wrote it.
